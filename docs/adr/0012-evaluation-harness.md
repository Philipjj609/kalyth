# 0012. Evaluation harness

Date: 2026-10-17. Status: accepted. Gate G6; builds on ADRs 0010 and 0011 and the Phase 0 review
(section 11).

## Context

The evaluation asks one question: does a model find the files a change needs more reliably from a
Kalyth context package than from plain retrieval, with the same model and the same context budget?
The answer is only credible under three conditions:

- the ground truth is fixed before anything runs on it;
- both conditions differ only in the context they give the model;
- every number can be traced back to recorded calls.

## Decision

**Ground truth.** The harness reads a truth file (`docs/evaluation`) and checks its SHA-256 against
the hash recorded when it was frozen. For a repository scenario it refuses to score unless the file
is `frozen` and the hash matches. The harness is developed and tested on a synthetic fixture with
its own truth. Its dry-run mode exercises the pipeline on the holdout repository without reading or
scoring any truth.

**Conditions.** In both, the final call is identical: the same model, the same instructions, the
same output schema (`files: [{path, reason}]`) and the same character budget for context.

- **Baseline:** lexical retrieval. Every text file at the pinned commit is split into chunks of 60
  lines and ranked by BM25 against the change request. Chunks are added in rank order until the
  budget is reached. Lockfiles, binaries and files over 200 kB are excluded.
- **Kalyth:**
  1. One seed call. The model sees the change request and the element catalogue with pinned
     excerpts, as the Navigator does, and names the existing elements the change touches directly.
  2. Kalyth compiles the context package for those seeds within the same budget, with typed impact
     paths (ADR 0011).
  3. The final call.

  The seed call's extra input is reported, not hidden: tokens and cost are shown per condition.

**Scoring.** Predicted paths are normalised. Paths that do not exist at the commit are counted as
unsupported and are not scored. Each run reports recall, precision and F1 against the truth, and
three runs per scenario and condition give the mean and range. Tokens, cost and latency come from
the gateway's call records.

**Records.** Real runs go through the gateway with a recording provider, so a report can be
regenerated by replay, byte for byte. The report states:

- the provider and models;
- whether the output is mock;
- the truth hash, commit and budget;
- the sample size.

It makes no claim of statistical significance.

## Alternatives

- **Embedding retrieval for the baseline.** It would need another paid model and would make the
  baseline depend on that model's quality. BM25 is free, deterministic and a common reference.
- **Running Kalyth's condition without a model in the seed step.** That would not compare like
  with like, because the seed choice is where the model's understanding of the request enters.

## Consequences

- Runs on Nebius need their own approved budget, as KAL-20261016-010 foresaw. Three scenarios, two
  conditions and three runs are 27 model calls.
- Mock runs exercise the pipeline and nothing more. Their scores say nothing about Kalyth and are
  labelled as mock output.
